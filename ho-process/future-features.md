# Future Features — Design Intent Register

## Purpose

This document tracks design decisions that are **deferred but not forgotten**.
Each entry records what we intend to build later and what Phase 1 must
preserve to make it possible. This prevents Phase 1 shortcuts from closing
doors we want open.

---

## F-001: Play-Time Narrative Generation (Option 3 Hybrid)

**Intent:** During gameplay, critical medical narrative (facts the player
needs to act on) is served from frozen pre-generated text. Flavor narrative
(emotional texture, character reactions, transitional descriptions, dialogue
variation) is generated by the LLM at play time via `LLMClient.narrate()`.

**Current Phase 1 approach:** Option 1 — all narrative pre-generated at
case creation time and frozen. No LLM calls during play.

**What Phase 1 must preserve:**
- Node content must have two distinct parts: `structured_data` (medical
  facts, always frozen) and `narrative_text` (description text, frozen
  now, swappable for dynamic generation later)
- Satori must emit structured events that contain enough context for an
  LLM to narrate from — even though the LLM isn't called yet
- Internal Affairs must consume narrative text through an interface that
  could be backed by either frozen text or an LLM call

**When to revisit:** Phase 3, after the vertical slice is stable and
multiple cases exist.

## F-002: Infocom-Style Expert Mode

**Intent:** An alternative input mode where advanced players type natural
language commands ("examine the patient's arms," "ask about her diet")
instead of selecting from a structured menu. The LLM parses intent and
maps to structured actions.

**Current Phase 1 approach:** Structured multiple-choice action menu only.

**What Phase 1 must preserve:**
- Actions must be internally represented as structured data (action type +
  subcategory + target), not as UI-specific constructs
- The action → Satori pathway must accept structured action objects from
  any source, not be coupled to a specific UI component

**When to revisit:** Phase 3+, after the core experience is solid.

## F-003: Case Builder Interface

**Intent:** A protected frontend tool for designing, generating, previewing,
and curating cases. Sits above Anamnesis. Allows seed selection, constraint
tuning, case preview, and approval workflow.

**Current Phase 1 approach:** Cases are generated via CLI/script. No GUI.

**What Phase 1 must preserve:**
- Anamnesis must expose a clean programmatic interface (not just a script)
  that accepts seeds and returns cases
- The seed format must be stable and documented

**When to revisit:** Phase 2, after multiple cases are being generated.

---

## F-004: Relational and Emotional Node Expansion

**Intent:** Full parity between medical nodes and relational/emotional
nodes. Relationships, trust dynamics, ethical dilemmas, and emotional
states should be as rich and consequential as medical findings.

**Current Phase 1 approach:** Relational nodes exist in the schema and
work mechanically, but the example case has only 1 relational node
out of 12. The system supports them; the content doesn't emphasize them yet.

**What Phase 1 must preserve:**
- Node types must include relational and emotional from day one
- Outcome evaluation must score relational outcomes separately from
  medical outcomes
- The node schema must not assume nodes are medical

**When to revisit:** Phase 2, when building cases with richer human dynamics.

---

## F-005: Teaching Layer Depth

**Intent:** Rich in-game education: tooltips on every action explaining
why it matters, optional deep dives into the medicine, post-case debriefs
that compare the player's path to the optimal path and explain what real
clinicians struggle with.

**Current Phase 1 approach:** Ground truth and optimal path exist in the
schema. Teaching content is minimal.

**What Phase 1 must preserve:**
- Ground truth must include optimal_path with enough detail for comparison
- Each node should have a `teaching_note` field (can be empty in Phase 1)
- Outcome evaluation must be detailed enough to support debrief generation

**When to revisit:** Phase 2, alongside case content expansion.

## F-006: Mobile/App Deployment

**Intent:** Ship Internal Affairs as a mobile app (iOS/Android) or
desktop app, not just a web application.

**Current Phase 1 approach:** SvelteKit web application only.

**What Phase 1 must preserve:**
- Frontend must communicate with Satori through a clean API, not through
  direct function imports or shared memory
- No browser-specific dependencies in core UI logic

**When to revisit:** Phase 3+, after the web experience is complete.

## F-007: Anamnesis Mode 3 — Fully Prompted Creative Generation

**Intent:** A third generation mode where the LLM receives the full
`CreativeSeed` as a rich prompt — including `dramatic_hook`,
`character_notes`, `narrative_inspiration`, `key_twists`,
`emotional_core`, and `forbidden_tropes` — and uses all of it when
constructing the case. Mode 3 supersedes Mode 2's partial injection
limitation.

**Current Phase 1 approach (Mode 2):** `CreativeSeed` carries all
creative fields, but `CaseGenerator.generate_case(seed: CaseSeed)` only
accepts a `CaseSeed`. Creative-only fields are constructed into a full
prompt via `build_creative_prompt(seed)`, but the prompt cannot yet be
passed to the provider. The pipeline logs a note at INFO level. Mode 2
therefore functions like Mode 1 with richer metadata captured in the
seed — the creative direction is recorded but not yet injected.

**What Phase 1 must preserve:**
- `build_creative_prompt()` must continue to produce a well-structured
  prompt string ready to pass to a provider when the interface supports it
- `CaseGenerator` interface must be designed so that a future
  `generate_case_with_prompt(seed, prompt: str)` overload is addable
  without breaking existing generators
- `CreativeSeed` and all its creative fields must remain stable — they
  are the source of truth for Mode 3 when it ships

**What needs to change in llm-client:**
- `CaseGenerator.generate_case()` (or a new method on it) must accept a
  `system_prompt` or `user_prompt` override that providers route to their
  respective API's system/user message slots
- `MockCaseGenerator` should accept a prompt and optionally vary output
  for test realism, or at minimum not reject the argument

**When to revisit:** Phase 2, after the first real provider integration is
validated end-to-end. Mode 3 is the target steady state for high-quality
case generation.

## F-008: Session Management Evolution

**Intent:** Move from in-memory session state to a fully stateless or
serialisable session model. Phase 1 uses an in-memory
`dict[str, SatoriEngine]` keyed by session ID on the FastAPI server.
A future iteration can swap this for serialised state (capture
`GameState` + action history → replay on demand) or a persistent
session store, without changing any frontend code.

**Current Phase 1 approach:** In-memory dict
(`session_manager.py`). Sessions are lost on process restart. No
persistence, no horizontal scaling. Acceptable for a single-case
local dev environment.

**Design principle applied (DIP):** The API is designed as if sessions
were stateless. Every response from `POST /api/sessions` and
`POST /api/sessions/{id}/actions` carries the **full renderable
state** — `GameState`, available actions, patient context, patient
condition, narrated events. The frontend never reads hidden server
state; it renders exactly what the last response contained. This
means swapping the session store is a server-side change only.

**What Phase 1 must preserve:**
- Every API response must be self-contained: no partial state, no
  references to "what the server told you before"
- Session ID must remain opaque to the frontend — it is a lookup key,
  not a semantic value
- `session_manager.py` must be isolated behind a thin interface so
  the storage implementation can be replaced without touching
  `main.py` or `models.py`

**What needs to change when revisiting:**
- Replace `dict[str, SatoriEngine]` with serialised `GameState` +
  action-log replay, or an external store (Redis, DB, etc.)
- Add session expiry / garbage collection
- Consider whether `CaseDefinition` needs to be stored or re-loaded
  from a case registry

**When to revisit:** Phase 2, when multi-user support or deployment
beyond localhost is needed.
